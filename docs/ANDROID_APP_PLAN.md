# Приложение для Android (Capacitor + офлайн-запись) — поэтапный план

Решение владельца (2026-10-19): **Capacitor** (оболочка вокруг готового сайта) + **своя маленькая очередь записей** (outbox) для офлайна. PowerSync/ElectricSQL — НЕ берём сейчас (отложено: понадобятся, если захотим полный local-first на нескольких устройствах). Переписывать на Flutter/React Native — нет. Задачи — в `docs/BACKLOG.md`, раздел **66**.

Принятые по умолчанию решения (владелец может изменить): сначала **APK по ссылке/GitHub Actions**, Play Store — позже (этап 5); iOS не делаем, но ничего не ломаем для него; уведомления и виджет — необязательный этап 4.

## Что уже есть (не изобретать заново)
- `manifest.json`, `sw.js` (кэш оболочки, `ld-shell-vNN`), `offline-cache.js` (офлайн-ЧТЕНИЕ последней копии в localStorage, ключ по `user.id`), `datacache.js`.
- Записи идут напрямую `supabase-js` (`.from(...).insert/upsert/update/delete`, `.rpc(...)`) из 18 пилотов `web-*/`. Баллы, стрики, лидерборд, друзья считаются SQL-функциями на сервере — они требуют сети и офлайн не нужны.
- Что реально нужно писать без сети: `water_log` (стакан воды), `daily_values` (метрики за день), `metrics` (создание/правка), `workout_entries`/`workout_exercises` (Тренировки), `daily_notes`, `body_parameter_values`. `profiles` (настройки, ~19 мест) офлайн-записи НЕ требует: пишем «по возможности», без очереди.

## Архитектура очереди (контракт — утверждается в 66.0, дальше не менять без согласования)
- Один модуль `offlineOutbox` (TypeScript, без Vue). Пилоты изолированы, поэтому файл лежит копией в каждом пилоте, которому нужен (`web-dashboard`, `web-header`, `web-workouts`, …) + страж-тест «копии одинаковы» (по образцу `waterAnim`/`collapseStyle`).
- Хранилище: IndexedDB (`ld-outbox`), НЕ localStorage; запись очереди одним транзакционным put.
- Операция: `{ id (uuid клиента), table, op: 'insert'|'upsert'|'update'|'delete', key, payload, clientTs, userId, attempts, lastError }`.
- Обёртка записи `writeThrough(op)`: сначала пытается онлайн; при сетевой ошибке (а не при ошибке RLS/валидации!) кладёт в очередь и возвращает «принято локально». Ошибки сервера (4xx) НЕ ретраятся бесконечно — уходят в «проблемные» с понятным текстом.
- Идемпотентность: id строк создаёт КЛИЕНТ (uuid) — повторная отправка = `upsert` по id, дублей не будет. Для `daily_values` ключ `(user_id, metric_id, date)`; для воды — id записи.
- Конфликты: «последний победил» по `updated_at`; для сумм дня (вода, подходы) — не перезаписывать, а добавлять записи (они уже построчные). Смещение часов: `clientTs` + защита от «будущего» (> сервер + 5 мин → берём серверное).
- Сброс очереди (`flush`): при `online`-событии, при старте и по таймеру; строго по порядку для одного ключа, параллельно для разных; экспоненциальная пауза; единственный «лидер» вкладки (Web Locks), чтобы две вкладки не слали одно и то же.
- Статус (для UI): `idle | offline | syncing | pending(N) | error(N)`, событие `outbox:change`.
- Баллы/стрики: сервер считает по дате ЗАПИСИ, а не по `now()` при синхронизации — проверить в 66.1 (иначе офлайн-день уйдёт в сегодня).

## Контракт (итог 66.0 + 66.1, утверждено)
Код: `web-dashboard/src/lib/offlineOutbox.ts` (эталон), копии в `web-header/src/lib/` и `web-workouts/src/lib/`, страж `web-dashboard/src/offlineOutboxCopies.test.ts`. Тесты: `offlineOutbox.test.ts`. Менять ВО ВСЕХ копиях сразу.

**API.** `createOutbox({client, storage?, now?, isOnline?})` → `write({key, table, op, payload?, match?, onConflict?})` → `{status:'sent'|'queued'|'rejected'}`; `flush()`, `list()`, `retry(id)`, `discard(id)`, `setUser(userId)`, `status()`/`subscribe()` (`idle|offline|syncing|pending|error` + счётчики `pending`/`failed`), `startAutoFlush(outbox)` (online, возврат на вкладку, таймер). Хранилища: `indexedDbStorage()` (рабочее) и `memoryStorage()` (тесты, заглушка для UI 66.4). Адаптер (66.5) вызывает `write` вместо прямого `supabase.from(...)`; `sent` — как раньше, `queued` — показать «ждёт синхронизации», `rejected` — обычная ошибка сервера.

**Что уточнил аудит таблиц.**
- У всех целевых таблиц uuid-PK с `default gen_random_uuid()` → клиент может задать `id` сам. Повторная вставка того же id даёт `23505` → очередь считает это «уже применено».
- `daily_values`: уникальность `(metric_id, date)`; пишем `upsert` с `onConflict`, ключ очереди `daily_values:<date>:<metric_id>`; подряд идущие upsert одного ключа склеиваются (уходит последний).
- Столбца `updated_at` нет → в v1 действует «победила последняя отправка по порядку очереди»; если понадобится честное «по времени», добавить столбец миграцией (отдельный пункт для 66.2).
- Баллы/стрики считаются при запросе по ДАТЕ записи, а не по `now()` в момент синхронизации → поздняя отправка офлайн-дня безопасна, день не «переезжает» в сегодня. Клиентские проверки достижений/искры после `flush` нужно перезапускать (задача адаптеров).
- Триггеры при записи (`goal_invite_on_note_done`, `metrics_pause_dates`, `metrics_skipped_days_guard`) могут отказать → это постоянная ошибка (код Postgres) → запись уходит в «проблемные» (`failed`), блокирует только свой ключ.
- Ошибки: сеть/таймаут/408/429/5xx — повтор с паузой 1с·2^n (до 60с); коды Postgres и 4xx — `failed`, сами не повторяются, ждут `retry`/`discard`.
- Порядок: внутри ключа строго по постановке; если по ключу уже что-то ждёт, новая запись встаёт следом, даже если сеть есть. Разные ключи не блокируют друг друга. Очередь привязана к `userId`.
- Проверено на PostgreSQL 16 (`scripts/sql_harness/scenario_066_offline_replay.sql`, запуск: `scripts/sql_harness/run.sh 103 scenario_066_offline_replay.sql`): повтор отправки не меняет баллы, поздняя доставка остаётся в дне записи и не рвёт серию, порядок доставки не важен, upsert заметки сохраняет planned_goals, повторная вставка с тем же uuid даёт 23505.
- Две вкладки: `flush` под Web Lock `ld-outbox-flush` (ifAvailable), без Web Locks — флаг в вкладке.

## Этапы
- **Этап 0 — решения и контракт** (1 агент, ~полдня, блокирует только API): 66.0.
- **Этап 1 — основа (параллельно)**: ядро очереди (66.1), сервер/SQL (66.2), оболочка PWA и вход без сети (66.3), UI офлайна на заглушке (66.4), каркас Capacitor (66.6).
- **Этап 2 — адаптеры записи (параллельно, после ядра)**: вода (66.5а), метрики/заметки/параметры тела (66.5б), Тренировки (66.5в).
- **Этап 3 — проверка**: офлайн-сценарии Playwright (66.7), чек-лист устройства (66.8).

## Правила для всех (напоминание)
- Версия по общему правилу (`X.YY`, после `.99` — следующий мажор); миграции берём «следующий свободный номер на момент коммита» (`ls migrations`), миграции этого эпика помечать комментарием `-- 66.x`.
- Копии библиотек в пилотах — только вместе со стражем; не править `App.vue`/`pageTabs.ts` «Кастомизации» без согласования с агентом 7.
- Ключи подписи Android (keystore), токены и пароли — НИКОГДА в репозиторий (только секреты GitHub у владельца).
- В облачной среде агентов нет Android SDK/эмулятора: APK собирает GitHub Actions или ПК владельца; проверка на телефоне — владелец (чек-лист 66.8).
- Каждая задача: тесты + `npm run build` + мутационная проверка + запись в ROADMAP/доску, как обычно.
