Доступ к GitHub
Каждый новый чат — новый контейнер, токен из прошлого чата не сохраняется.
Попроси у пользователя свежий токен (fine-grained PAT, права Contents: Read
and write, ограниченный репозиториями vlsek/life-dashboard и vlsek/portfolio)
прямо в новом чате. Токен НИКОГДА не пиши в файлы, коммиты, COORDINATION.md
и не оставляй в git remote/config. Безопасный способ (токен только в памяти
команды):
  AUTH=$(printf 'x-access-token:%s' "$TOKEN" | base64 -w0)
  git -c http.extraheader="Authorization: Basic $AUTH" clone https://github.com/vlsek/<repo>.git
  (то же -c http.extraheader=... для fetch / pull / push)
Личность для коммитов: у каждого агента своя, формат
"Agent N <agentN@users.noreply.github.com>" (git config user.name/user.email в
клоне). Номер агента бери из COORDINATION.md (свободный блок) или у
пользователя. После сессии предложи пользователю отозвать токен.
Репозиторий life-dashboard ПУБЛИЧНЫЙ (проверено 2026-09-28) — учитывай это при
любых коммитах.
ГРАБЛИ С ТОКЕНОМ (2026-09-30): не клонируй как `https://x-access-token:<TOKEN>@github.com/...` —
токен остаётся в `.git/config` (remote origin). Если так вышло — сразу
`git remote set-url origin https://github.com/vlsek/<repo>.git` и дальше только через
`-c http.extraheader=...`. Список доступных репозиториев (если название не сказали):
`GET https://api.github.com/user/repos` с тем же токеном; в bash-контейнере доступны
github.com/api.github.com/registry.npmjs.org, остальное закрыто.

Как работает команда агентов (важно, если ты «Агент N»)
- Номер агента даёт пользователь или свободный блок в COORDINATION.md. Идентичность коммитов:
  «Agent N <agentN@users.noreply.github.com>». Протокол заявки/закрытия — в COORDINATION.md; коротко:
  заявка отдельным коммитом ТОЛЬКО с COORDINATION.md и сразу push → работа → бамп версии после git fetch
  (следующий свободный номер) → changelog RU+EN → запись в ROADMAP.md → закрыть блок, `[x]` в бэклоге,
  строка в журнал → pull --rebase → push. Чужие блоки не править; зависший блок (>1 суток без коммитов)
  не перехватывать самому — спросить пользователя.
- Когда пользователь говорит «бери любые задачи из фазы 3» — выбирай сам, но каждую помечай `[~ агент N]`
  до начала и `[x] (vX.YY, агент N)` после; новые находки записывай в бэклог строкой `[ ]`.
- Время в changelog/журнале — момент ЗАВЕРШЕНИЯ работы (перед коммитом), локальное время пользователя
  (Вильнюс). Часы контейнеров агентов расходятся, порядок версий важнее минут.
- Переполнение контекста случалось не раз (v1.19, v1.22, v1.25, v1.27, v1.28): работа, не дошедшая до
  коммита, теряется. Поэтому: заявка — сразу, коммитить и пушить небольшими законченными шагами.

Грабли процесса (набрано за фазы 1–3)
- `npm run build` сразу во всех пилотах параллельно роняет web-dashboard по памяти («Killed») — собирать
  дашборд отдельно. После правки общего куска (AppShell.vue, i18n и т.п.) пересобирать КАЖДЫЙ затронутый пилот
  и проверять grep по бандлам на старые адреса (`<стр>-vue`).
- В bash-контейнере вывод с кириллицей: `cut -c`/`head -c` по байтам ломают UTF-8 и инструмент
  отвечает «invalid UTF-8» — печатай файлы целиком или через python (`open(..., encoding='utf-8')`).
- Внутри пилота, где добавляется i18n-ключ, словарь СВОЙ (web-<стр>/src/lib/i18n.ts, EN и RU секции);
  общий i18n.js — только для классики.
- Поле в JSON `sets[]` у тренировок (reps/weight/time/duration/side) читают и классика, и рекорды, и
  графики — новые возможности формы (например, «Утяжеление» пишется в `weight`, Л/П — в `side`) не должны
  менять формат хранения без миграции. Слой «строк формы» — web-workouts/src/lib/sides.ts.
- В CSS-комментариях (и в `<style>` компонентов) НЕЛЬЗЯ писать звёздочку со слэшем, даже в тексте вроде «web-*/src/style.css»:
  она закрывает комментарий досрочно, остаток ломает разбор, и СЛЕДУЮЩЕЕ правило молча исчезает из сборки (v2.05, нашла агент 7 только
  проверкой собранного css). После правки CSS — `cat <стр>/assets/*.css | grep -c '<кусок нового правила>'`.
- В пилотах настоящая проверка типов — `npm run build` (`vue-tsc -b`), а не `npx vue-tsc --noEmit`: последний файлы приложения не
  проверяет и «зелёный» ничего не значит. Тест, читающий файлы репозитория, — через `// @ts-ignore` над `import ... from 'node:fs'` и
  относительные пути от папки пилота (vitest запускается из `web-<стр>/`), как `motionOff.test.ts`.
- Тест-страж `web-dashboard/src/motionAllPilots.test.ts` требует у КАЖДОЙ новой страницы `web-<стр>/`: правило `html[data-motion='off'] *`
  в `src/style.css`, ранний скрипт `site_motion` в `index.html` ПЕРЕД основным модулем и это же правило в собранном css.
- Собранная папка пилота (`dashboard/`, `workouts/` и т.д.) — единственное, что почти всегда конфликтует между агентами: хеши в
  `index.html` и имена бандлов. НЕ делать `git stash` → `pull` → `stash pop` со скриптом релиза одной командой: при конфликте скрипт
  продолжит и запушит `index.html` с маркерами `<<<<<<<` (так было при v1.54/v1.55, страница была сломана пару минут). Правильно: сначала
  закоммитить, потом `git pull --rebase`; при конфликте в собранной папке — взять любую сторону, ПЕРЕСОБРАТЬ пилот из слитых исходников
  (`npm run build`) и только потом пушить. После пуша: `git show origin/main:<пилот>/index.html | grep -c '<<<<<<<'` должен дать 0,
  а `python3 scripts/check_dead_links.py` — OK. Номер версии перечитывать из `config.js` после последнего `pull`, а не запоминать заранее. Формат — `X.NN` с ДВУЗНАЧНОЙ минорной частью (`2.07` → `2.08`, а не `2.8`): при автоинкременте скриптом форматировать `f'{minor:02d}'`.
- Вода «выполнена» по ЭФФЕКТИВНОЙ норме (v1.92, миграция 033): ручная `goal_value` → авто по последнему весу (вес × 30) → 2000. Правило живёт в `lib/waterGoal.ts` (одинаковая копия в web-dashboard, web-shop, web-header,
web-history, web-achievements) и зеркалит SQL-помощники `is_water_like`/`is_weight_like`/`water_auto_norm_ml`/`metric_null_goal` — менять ВМЕСТЕ. Любой новый загрузчик метрик, из которого считаются баллы/«выполнено»/кольца/стрики, пропускает их через
  `withWaterGoal(userId, metrics)`; метрики для формы редактирования — НЕТ (иначе в `goal_value` запишется авто-норма). миграция `033_water_effective_norm.sql` применена владельцем (проверка — `docs/sql-checks/033_water_effective_norm_check.sql`). Следующая свободная миграция — 049 (048 — агент 2, кастомизация: `user_customizations` + `profiles.customization`) — сверяйся с `ls migrations/` и блоками в COORDINATION (047 — агент 2, публичные значки; 045 — агент 1, дробные баллы за подходы: применять ПОСЛЕ 044, `numeric` вместо `int` в пяти функциях баллов/лидерборда — новые миграции, которые переопределяют эти функции, строить на определениях из 045; 046 — агент 2: `get_leaderboard_period` для периодов Сообщества, отдельная функция, `get_leaderboard` не трогает; 039 занята агентом 6 «Достижения», 040 — агентом 7 «Программы», 041 — агентом 1 «подходов в день по плану» (`planned_sets_log`), 042 — челленджи `source_exercise`, 043 — норма воды с поправкой на еду, 044 — агентом 1: серверные серии/баллы/лидерборд по правилу «подходов в день» (применять 041, затем 044; 044 сама добавит колонку, если 041 нет); перед созданием новой — `ls migrations/` после fetch; ранее: 034 — рост, 035 — избранное, 036 — журнал воды `water_log`, применена владельцем 2026-10-03: `lib/waterLog.ts` общий для `web-dashboard` и `web-header`, менять ВМЕСТЕ; запись в журнал best-effort — сумма дня в `daily_values` источник правды; без таблицы окно воды берёт запасной журнал из стека «Отменить»).
