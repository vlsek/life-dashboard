Доступ к GitHub
Каждый новый чат — новый контейнер, токен из прошлого чата не сохраняется.
Попроси у пользователя свежий токен (fine-grained PAT, права Contents: Read
and write, ограниченный репозиториями vlsek/life-dashboard и vlsek/portfolio)
прямо в новом чате. Токен НИКОГДА не пиши в файлы, коммиты, COORDINATION.md
и не оставляй в git remote/config. Безопасный способ (токен только в памяти
команды):
  AUTH=$(printf 'x-access-token:%s' "$TOKEN" | base64 -w0)
  git -c http.extraheader="Authorization: Basic $AUTH" clone https://github.com/vlsek/<repo>.git
  (то же -c http.extraheader=... для fetch / pull / push)
Личность для коммитов: у каждого агента своя, формат
"Agent N <agentN@users.noreply.github.com>" (git config user.name/user.email в
клоне). Номер агента бери из COORDINATION.md (свободный блок) или у
пользователя. После сессии предложи пользователю отозвать токен.
Репозиторий life-dashboard ПУБЛИЧНЫЙ (проверено 2026-09-28) — учитывай это при
любых коммитах.

Стек
Фронтенд: чистый HTML/CSS/JS, без сборки, без фреймворков. Бэкенд: Supabase
(Postgres + Auth + RLS), проект haxmgtflegsfpxieaydv. Google OAuth настроен и
работает. PWA: manifest.json + иконки. Хостинг: Cloudflare Workers, деплой
через wrangler deploy без wrangler.toml, автодеплой на пуш в main. Без
index.html в корне сборка падает ("Could not detect a directory containing
static files") — в life-dashboard он есть как заглушка с редиректом на
/login.html. _redirects (фишка Pages) тут не работает вообще.

Версионирование — важный установившийся процесс
SITE_VERSION в config.js — бампается на +0.01 при каждом заходе с изменениями.
Рядом — CHANGELOG_RU / CHANGELOG_EN, массивы {version, date, changes: [...]}.
С недавних пор date включает и время ("2026-09-26 12:40"), не только дату —
показывается пользователю по клику на номер версии в сайдбаре.
После любой правки JS — обязательно node --check <file>.js на все изменённые
файлы перед коммитом.

Архитектурные паттерны — не изобретать заново
Кастомные select: enhanceSelectWithCustomDropdown(selectElement) в config.js.
Плавающие списки: positionFloatingPanel(anchor, panel) — position:fixed
относительно экрана, не родителя (осознанно, из-за обрезки overflow-контейнерами
на телефоне). Модалки: .modal-backdrop/.modal, см. openModal() в config.js для
форм с полями (включая тип "icon" — выбор SVG-иконки с поиском, см. ниже) или
ручная сборка для нестандартной разметки. Точечное обновление вместо
переполнения блоков: держать ссылку на узкий host-элемент, обновлять именно
его. Для функций, которые МОГУТ вызываться параллельно — обёртка с флагом
Running/Queued (см. refreshStreakBadge()/loadProfile() как готовые примеры).
i18n: i18n.js, translations.en/ru, функция t(key); строки с ведущим эмодзи
автоматически рисуются как SVG-иконки через tIcon()/setI18nText() — см.
LEADING_EMOJI_ICONS. PWA-иконки монохрома пересобираются через rsvg-convert
(apt-get install librsvg2-bin), силуэт должен помещаться в safe zone (см.
историю коммитов v0.48).

Кэш данных (datacache.js) — ускорение, не трогать бездумно
Список метрик и вся история значений/заметок грузятся один раз и кэшируются;
после записи перезапрашиваются только затронутые даты. Обёртка вокруг
sb.from() ловит insert/update/upsert/delete по metrics/daily_values/
daily_notes и сама инвалидирует кэш. Supabase отдаёт максимум 1000 строк за
запрос — история читается постранично (fetchAllRows), это важно помнить при
любых новых местах, где читается daily_values/daily_notes целиком (в т.ч. в
пилоте на Vue — там та же пагинация продублирована вручную).

SVG-иконки вместо эмодзи
config.js: ICON_PATHS — библиотека из 90 иконок (фитнес, здоровье, еда,
дом/быт, финансы, природа, путешествия, техника, хобби, питомцы и т.д.),
iconSvg(name)/setIcon(el,name) — вставить иконку. Для метрик и параметров
тела: buildIconPicker(current) — сетка иконок с полем поиска (ICON_KEYWORDS,
ищет и по-русски, и по-английски) + полем для своего эмодзи. metricIconKey()/
iconHtml()/iconText()/labelHtml() — автоматически рисуют уже сохранённые
эмодзи их SVG-аналогом (EMOJI_TO_SVG), если он есть, не трогая данные
пользователя.

Расписания метрик (miграция 021, дополнена в 025)
metrics.schedule (jsonb): null = каждый день; {type:"days", days:[0..6]} =
только в эти дни недели (0=воскресенье); {type:"weekly", min:N} = не реже N
раз в неделю; {type:"at_most", max:N} = не чаще N раз в неделю. Вся логика
(что считается "нужным сегодня", как не рвётся стрик, как считается процент
дня/недели) — в config.js (metricSchedule/metricExpectedOn/metricCountsInDay)
и dashboard.js (computeStreakSkipping/computeWeeklyStreak и их at_most-аналог).
Та же логика продублирована (портирована 1:1, с тестами) в web-history/.

ЧАСТЬ 2 — ПИЛОТ ПЕРЕЕЗДА НА НОВЫЙ СТЕК (web-history/)
===================================================================

Контекст решения
Обсуждали переезд на Astro+TS+Tailwind, затем на Vite+React/Vue/Svelte+TS+
Tailwind. Решили: не переписывать всё разом (риск регрессий на 60+ версиях
уже стабильного кода), а мигрировать постепенно, начиная с ОДНОЙ
самостоятельной страницы. Выбрали Vue 3 (Composition API + <script setup>) —
ближе всего по духу к нынешним HTML+JS страницам, зрелая документация.
Выбрали Vite (не Astro) — сайт не контентный, а насквозь интерактивный,
Astro тут не даёт преимуществ. TypeScript — типы. Tailwind — утилитарные
классы вместо ручного style.cssText.

ВАЖНОЕ ПРАВИЛО: версия основного сайта (SITE_VERSION в config.js) при каждой
итерации переезда на новый стек поднимается только на +0.01, независимо от
объёма проделанной работы в этой итерации (в отличие от обычной feature-
разработки, где размер бампа решается по объёму). В CHANGELOG для таких
коммитов — короткая запись про сам факт шага пилота, без подробностей на
уровне обычных фич.

Фаза 2 — рецепт переезда одной страницы (на примере History, v1.14)

следующей страницы (Skills/Goals могли решить детали иначе, если они запушены раньше —
сверься с их коммитами, но общая канва такая):

2. Собрать (npm run build) в новую папку ../<page>, удалить старую <page>-vue/ (git rm -r).
3. Классические <page>.html + <page>.js → git mv в legacy/. Внутри .html поправить
   относительные пути на общие файлы (favicon.svg, style.css, i18n.js, theme.js, config.js,
   offline-cache.js, datacache.js) с "x" на "../x" — они теперь на уровень выше. Сам
   <page>.js остаётся рядом (переехал вместе), путь к нему не трогать. manifest.json,
   /icons/... и Supabase-preconnect уже абсолютные — не трогать.
4. config.js: в pages[] изменить href этой страницы на "legacy/<page>.html" (без ведущего
   слэша — navHref() в renderNav() сам нормализует). Поле vue у неё же — на "<page>/".
   ВАЖНО: pages[] используют ВСЕ классические страницы разом (общий файл) — здесь меняется
   только ОДНА строка твоей страницы, остальные агенты фазы 2 меняют свою. Сам механизм
   navHref() (нормализация относительных/абсолютных href в renderNav(), 4 места присвоения
   .href) уже есть, трогать не нужно — если у тебя более старая копия репозитория без него,

5. sw.js: в ASSETS убрать "/<page>.html","/<page>.js", добавить "/legacy/<page>.html",

6. Все 12 AppShell.vue: href этой страницы в общем nav-массиве с '/<page>-vue/' на '/<page>/'.
7. Проверить репозиторий целиком на другие упоминания "<page>-vue" и "<page>.html" вне

7а. ПЕРЕСОБРАТЬ КАЖДЫЙ ПИЛОТ, у которого менялся исходник (AppShell.vue и т.п.): npm run build в

  синхронизации — потому что страница на том же домене
  (life-dashboard.orneryhero.workers.dev/history-vue/), и supabase-js по
  умолчанию хранит сессию в localStorage под одним и тем же ключом. Если
  когда-нибудь пилот переедет на другой домен/поддомен — это перестанет
  работать само, придётся передавать сессию явно.
- Пагинация Supabase (>1000 строк) — продублирована в
  useHistoryData.ts (fetchAllRows), тот же фикс, что и в vanilla v0.56.
- Тема (src/lib/theme.ts) — тот же localStorage-ключ site_theme, те же 4
  темы, CSS-переменные скопированы дословно в src/style.css.
- Язык (src/lib/i18n.ts) — тот же localStorage-ключ site_lang, но словарь
  СВОЙ, маленький, только под нужды этой страницы (i18n.js целиком не
  модульный, чтобы его импортировать). При переносе следующей страницы —
  либо расширять этот словарь, либо наконец сделать i18n.js импортируемым.
- Шапка + выезжающее по свайпу боковое меню (AppShell.vue) — тот же
  localStorage, тот же свайп (центральная зона экрана, порог 70px, защита
  от вертикального скролла), ссылки на все остальные (ванильные) страницы
  по абсолютным путям.

  неважным на текущем этапе.

Возможные следующие шаги (не начато, на усмотрение)
- Перенести install/tour/about в пилот, если он приживётся.
- Перенести вторую страницу (кандидаты: Milestones или Calendar — не тянут
  сложных живых пересчётов, как Dashboard).
- Общий модуль SVG-иконок в TS (портировать ICON_PATHS/buildIconPicker).
- Сделать i18n.js на ванильном сайте импортируемым модулем, чтобы не
  дублировать словари между стеками.

  отдельный проект в любом случае, независимо от веб-стека).
