Доступ к GitHub
Каждый новый чат — новый контейнер, токен из прошлого чата не сохраняется.
Попроси у пользователя свежий токен (fine-grained PAT, права Contents: Read
and write, ограниченный репозиториями vlsek/life-dashboard и vlsek/portfolio)
прямо в новом чате. Токен НИКОГДА не пиши в файлы, коммиты, COORDINATION.md
и не оставляй в git remote/config. Безопасный способ (токен только в памяти
команды):
  AUTH=$(printf 'x-access-token:%s' "$TOKEN" | base64 -w0)
  git -c http.extraheader="Authorization: Basic $AUTH" clone https://github.com/vlsek/<repo>.git
  (то же -c http.extraheader=... для fetch / pull / push)
Личность для коммитов: у каждого агента своя, формат
"Agent N <agentN@users.noreply.github.com>" (git config user.name/user.email в
клоне). Номер агента бери из COORDINATION.md (свободный блок) или у
пользователя. После сессии предложи пользователю отозвать токен.
Репозиторий life-dashboard ПУБЛИЧНЫЙ (проверено 2026-09-28) — учитывай это при
любых коммитах.
ГРАБЛИ С ТОКЕНОМ (2026-09-30): не клонируй как `https://x-access-token:<TOKEN>@github.com/...` —
токен остаётся в `.git/config` (remote origin). Если так вышло — сразу
`git remote set-url origin https://github.com/vlsek/<repo>.git` и дальше только через
`-c http.extraheader=...`. Список доступных репозиториев (если название не сказали):
`GET https://api.github.com/user/repos` с тем же токеном; в bash-контейнере доступны
github.com/api.github.com/registry.npmjs.org, остальное закрыто.

Грабли процесса (набрано за фазы 1–3)
- `npm run build` сразу во всех пилотах параллельно роняет web-dashboard по памяти («Killed») — собирать
  дашборд отдельно. После правки общего куска (AppShell.vue, i18n и т.п.) пересобирать КАЖДЫЙ затронутый пилот
  и проверять grep по бандлам на старые адреса (`<стр>-vue`).
- В bash-контейнере вывод с кириллицей: `cut -c`/`head -c` по байтам ломают UTF-8 и инструмент
  отвечает «invalid UTF-8» — печатай файлы целиком или через python (`open(..., encoding='utf-8')`).
- Внутри пилота, где добавляется i18n-ключ, словарь СВОЙ (web-<стр>/src/lib/i18n.ts, EN и RU секции);
  общий i18n.js — только для классики.
- Поле в JSON `sets[]` у тренировок (reps/weight/time/duration/side) читают и классика, и рекорды, и
  графики — новые возможности формы (например, «Утяжеление» пишется в `weight`, Л/П — в `side`) не должны
  менять формат хранения без миграции. Слой «строк формы» — web-workouts/src/lib/sides.ts.
- Собранная папка пилота (`dashboard/`, `workouts/` и т.д.) — единственное, что почти всегда конфликтует между агентами: хеши в
  `index.html` и имена бандлов. НЕ делать `git stash` → `pull` → `stash pop` со скриптом релиза одной командой: при конфликте скрипт
  продолжит и запушит `index.html` с маркерами `<<<<<<<` (так было при v1.54/v1.55, страница была сломана пару минут). Правильно: сначала
  закоммитить, потом `git pull --rebase`; при конфликте в собранной папке — взять любую сторону, ПЕРЕСОБРАТЬ пилот из слитых исходников
  (`npm run build`) и только потом пушить. После пуша: `git show origin/main:<пилот>/index.html | grep -c '<<<<<<<'` должен дать 0,
  а `python3 scripts/check_dead_links.py` — OK. Номер версии перечитывать из `config.js` после последнего `pull`, а не запоминать заранее.
- Не все миграции применены у владельца: без миграции фича должна быть скрыта, а не показываться

Кэш данных (datacache.js) — ускорение, не трогать бездумно
Список метрик и вся история значений/заметок грузятся один раз и кэшируются;
после записи перезапрашиваются только затронутые даты. Обёртка вокруг
sb.from() ловит insert/update/upsert/delete по metrics/daily_values/
daily_notes и сама инвалидирует кэш. Supabase отдаёт максимум 1000 строк за
запрос — история читается постранично (fetchAllRows), это важно помнить при
любых новых местах, где читается daily_values/daily_notes целиком (в т.ч. в
пилоте на Vue — там та же пагинация продублирована вручную).

SVG-иконки вместо эмодзи
config.js: ICON_PATHS — библиотека из 90 иконок (фитнес, здоровье, еда,
дом/быт, финансы, природа, путешествия, техника, хобби, питомцы и т.д.),
iconSvg(name)/setIcon(el,name) — вставить иконку. Для метрик и параметров
тела: buildIconPicker(current) — сетка иконок с полем поиска (ICON_KEYWORDS,
ищет и по-русски, и по-английски) + полем для своего эмодзи. metricIconKey()/
iconHtml()/iconText()/labelHtml() — автоматически рисуют уже сохранённые
эмодзи их SVG-аналогом (EMOJI_TO_SVG), если он есть, не трогая данные
пользователя.

Расписания метрик (miграция 021, дополнена в 025)
metrics.schedule (jsonb): null = каждый день; {type:"days", days:[0..6]} =
только в эти дни недели (0=воскресенье); {type:"weekly", min:N} = не реже N
раз в неделю; {type:"at_most", max:N} = не чаще N раз в неделю. Вся логика
(что считается "нужным сегодня", как не рвётся стрик, как считается процент
дня/недели) — в config.js (metricSchedule/metricExpectedOn/metricCountsInDay)
и dashboard.js (computeStreakSkipping/computeWeeklyStreak и их at_most-аналог).

Контекст решения
Обсуждали переезд на Astro+TS+Tailwind, затем на Vite+React/Vue/Svelte+TS+
Tailwind. Решили: не переписывать всё разом (риск регрессий на 60+ версиях
уже стабильного кода), а мигрировать постепенно, начиная с ОДНОЙ
самостоятельной страницы. Выбрали Vue 3 (Composition API + <script setup>) —
ближе всего по духу к нынешним HTML+JS страницам, зрелая документация.
Выбрали Vite (не Astro) — сайт не контентный, а насквозь интерактивный,
Astro тут не даёт преимуществ. TypeScript — типы. Tailwind — утилитарные
классы вместо ручного style.cssText.

ВАЖНОЕ ПРАВИЛО: версия основного сайта (SITE_VERSION в config.js) при каждой
итерации переезда на новый стек поднимается только на +0.01, независимо от
объёма проделанной работы в этой итерации (в отличие от обычной feature-
разработки, где размер бампа решается по объёму). В CHANGELOG для таких
коммитов — короткая запись про сам факт шага пилота, без подробностей на
уровне обычных фич.

Фаза 2 — рецепт переезда одной страницы (на примере History, v1.14)
Короткий адрес без -vue для пилота, классика — в /legacy/<имя>.html. Порядок для
следующей страницы (Skills/Goals могли решить детали иначе, если они запушены раньше —
сверься с их коммитами, но общая канва такая):
1. web-<page>/vite.config.ts: base и build.outDir с '/<page>-vue/' на '/<page>/'.
2. Собрать (npm run build) в новую папку ../<page>, удалить старую <page>-vue/ (git rm -r).
3. Классические <page>.html + <page>.js → git mv в legacy/. Внутри .html поправить
   относительные пути на общие файлы (favicon.svg, style.css, i18n.js, theme.js, config.js,
   offline-cache.js, datacache.js) с "x" на "../x" — они теперь на уровень выше. Сам
   <page>.js остаётся рядом (переехал вместе), путь к нему не трогать. manifest.json,
   /icons/... и Supabase-preconnect уже абсолютные — не трогать.
4. config.js: в pages[] изменить href этой страницы на "legacy/<page>.html" (без ведущего
   слэша — navHref() в renderNav() сам нормализует). Поле vue у неё же — на "<page>/".
   ВАЖНО: pages[] используют ВСЕ классические страницы разом (общий файл) — здесь меняется
   только ОДНА строка твоей страницы, остальные агенты фазы 2 меняют свою. Сам механизм
   navHref() (нормализация относительных/абсолютных href в renderNav(), 4 места присвоения
   .href) уже есть, трогать не нужно — если у тебя более старая копия репозитория без него,
   подтяни main перед началом.
5. sw.js: в ASSETS убрать "/<page>.html","/<page>.js", добавить "/legacy/<page>.html",
   "/legacy/<page>.js". Бампнуть CACHE_NAME (ld-shell-vN → vN+1) — иначе у уже установленных
   пользователей старый путь останется в кэше.
6. Все 12 AppShell.vue: href этой страницы в общем nav-массиве с '/<page>-vue/' на '/<page>/'.
7. Проверить репозиторий целиком на другие упоминания "<page>-vue" и "<page>.html" вне
   самой страницы (грепом) — например комментарий в web-<page>/src/lib/supabase.ts со
   старым путём в примере URL, если он там есть.
7а. ПЕРЕСОБРАТЬ КАЖДЫЙ ПИЛОТ, у которого менялся исходник (AppShell.vue и т.п.): npm run build в
   каждой web-<x>/. Прод раздаёт собранные бандлы (*-vue/assets, history/, calendar/, shop/), а не
   исходники — без пересборки ссылки в меню остаются старыми, а после git rm старой <page>-vue/
   ведут в 404 (так было в 1.14/1.15, починено в 1.16). Проверка: grep -l "<page>-vue"
   */assets/*.js должно быть пусто. Ещё места вне AppShell: classic dashboard.js (клик по балансу),
   web-dashboard/ProfileSection.vue + его тест — грепать и по <page>.html, и по <page>-vue.
   Ещё: напоминания в classic dashboard.js / пилоте Дашборда (ReminderBanners.vue) ссылаются на страницу
   (вехи — `milestones.html`, найдено в v1.25) — грепать `<page>.html` в dashboard.js и `<page>-vue` в web-dashboard/src.
8. node --check на все тронутые .js, vue-tsc --noEmit + vitest run в web-<page>/ и в паре
   других пилотов (AppShell.vue общий), npm run build. Версия/changelog RU+EN, запись в
   ROADMAP.md и COORDINATION.md (блок + журнал), git pull --rebase перед финальным push.
7б. Заглушка старого адреса: добавь строку `"<page>.html": "/<page>/"` в STUBS `scripts/gen_redirect_stubs.py` и запусти его
   (корневой <page>.html — редирект с сохранением ?query и #hash; иначе закладки на старый адрес дадут 404).
ГРАБЛИ (нашёл агент 1, v1.23): любой редирект/ссылка на другую страницу внутри классических .js/config.js
должен быть АБСОЛЮТНЫМ (`/login.html`, не `login.html`) — со страницы в /legacy/ относительный путь ведёт на
/legacy/<...> и даёт 404. После каждого переезда: grep `location.href *= *"[a-z-]+\.html"` по legacy/ и config.js.
Обратная ссылка пилот→классика сделана агентом 7 (v1.39): плашки pilot_badge нет, внизу выдвижного
меню каждого AppShell.vue — неприметная `legacy-<стр>` (константа `classicHref`, ведёт на
/legacy/<имя>.html; старые корневые адреса — только редирект-заглушки, на них НЕ ссылаться).
ПЕРЕД ПУШЕМ: python3 scripts/check_dead_links.py (без сети; ловит ссылки на несуществующие адреса в классике, legacy/,
исходниках пилотов, pages[] в config.js, sw.js ASSETS, manifest.json и в собранных <страница>/index.html; проверено
мутационным тестом на 4 видах поломок). Заодно сверяет base из vite.config.ts с папкой сборки.

Актуальное состояние пилота (на v1.36)
Каждая страница — отдельный mini-Vite-проект web-<page>/ → /<page>/ со своими копиями общих кусков (код
между страницами не импортируется, а копируется: AppShell.vue, i18n.ts, supabase.ts, chart.ts и т.д.).
Перенесены все 14 страниц: history, milestones, calendar, goals, skills, shop, languages (web-languages/,
НЕ web-english/), community (с «Сравнением по активностям» и друзьями), account, challenges, workouts
(графики, Утяжеление, Л/П одним блоком, разминка), dashboard (блоки: профиль, дневные метрики, подходы,
планы, графики, стрики, вода, кольца, напоминания; раскладка и сворачивание секций), login, onboarding.
Общие механизмы: событие dashboard:data-changed (lib/events.ts), общий код графиков (chart.ts, ChartBlock,
PeriodPicker, CustomPeriodModal), календарная арифметика дат через addDaysIso/parseIso, а НЕ «мс от
new Date("YYYY-MM-DD")» (UTC-полночь ломает даты западнее UTC и в ночь перевода часов), чтение больших
таблиц — только постранично (Supabase отдаёт ≤1000 строк). Install-модалка, приветственный тур, «О проекте»
и SVG-иконки в пилот уже портированы (см. web-workouts/src/components и lib/icons.ts как образец).

Что уже сделано (страница "История" на Vue)
Папка web-history/ внутри репозитория life-dashboard — исходники Vite-проекта
(package.json, src/, vite.config.ts, vitest.config.ts). node_modules и dist
там в .gitignore, НЕ коммитятся. Собранный билд копируется Vite'ом напрямую
в ../history (см. outDir в vite.config.ts; до v1.14 — ../history-vue) — это отдельная папка в
корне репозитория life-dashboard, она и коммитится, и раздаётся тем же
Cloudflare Workers деплоем по адресу /history/.

Как собрать после правок:
  cd web-history && npm install (если ещё не ставили) && npm run build
Собранный результат появится в ../history — закоммитить его вместе с
исходниками в src/.

Тесты (обязательно перед коммитом):
  cd web-history && npm run test
Исходно было 12 тестов, сейчас у каждого пилота свои (Vitest + happy-dom + @vue/test-utils; числа — в журнале COORDINATION): 6 сверяют dayStats/
weekStats с вручную проверенными числами оригинальной ванильной history.js
(dayStats/weekStats портированы построчно, семантика включая at_most/weekly
расписания и бонусные ⭐-пункты сохранена), 3 монтируют DayDetailModal
целиком, 3 — AppShell (шапка+сайдбар). При любой правке логики — сверяться
с этими тестами, при добавлении новой логики — добавлять новые тесты по
той же схеме (ожидаемые числа брать из работающей ванильной версии, а не
придумывать).

Что не перенесено / открыто по пилоту (на 2026-09-30)
- Пуш-уведомления при закрытой странице (Планы, вечернее напоминание работают только пока страница открыта).
- Admin (admin.html) — пилота НЕ будет: служебная страница остаётся в корне как есть (решение владельца, 2026-09-30, подтверждено повторно). Не переносить и не делать пилот, если владелец сам не попросит.
- Оформление у части страниц — на глаз, не пиксель-в-пиксель со style.css (Tailwind preflight слегка
  меняет базовые размеры). Известные визуальные хвосты: чекбоксы без акцентного цвета вне Дашборда (BACKLOG 7.2).

Возможные следующие шаги — смотри docs/BACKLOG.md (фаза 3) и «Открыто (главное)» выше. Про будущий
Android/iOS (фаза 4): Vite/Vue не мешает ни PWA-пути (vite-plugin-pwa вместо ручной генерации иконок/
манифеста), ни обёртке через Capacitor; полностью нативный React Native/Flutter — отдельный проект в любом случае.

Если пользователь просит правки в КЛАССИКЕ (legacy/*.js, config.js) — просто
открой нужный файл в текущем состоянии репозитория и работай как обычно:
правка → node --check → бамп версии (+0.01, или больше для обычных фич) +
changelog на обоих языках с датой и временем → коммит → пуш. Если просит работать
в ПИЛОТЕ — работай в web-<стр>/, гоняй `npx vitest run` и `npx vue-tsc --noEmit`, собирай
(`npm run build`), коммить исходники + собранную папку /<стр>/; версия — следующий свободный номер
после git fetch (+0.01 для итераций переезда, для фич — по объёму).
