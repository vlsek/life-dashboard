ГЛАВНОЕ ПРАВИЛО ПАРАЛЛЕЛЬНОЙ РАБОТЫ
===================================================================

Три репозитория = три изолированных лабиринта. Между ними конфликтов не будет
никогда, потому что это разные git-клоны, разные пуши:
  A) vlsek/portfolio — полностью независим от остального.
  B) vlsek/life-dashboard, папки web-<page>/ (+ <page>-vue/ на выходе сборки)
     — Vue-пилот, по одной независимой паре папок на каждую перенесённую
     страницу.
  C) vlsek/life-dashboard, всё остальное — ванильный сайт.

(B) и (C) — ОДИН репозиторий. Агенты на (B) и на (C) МОГУТ работать
параллельно и пушить в main без конфликтов, ПОКА не трогают одни и те же
файлы.

ПОДТВЕРЖДЕНО НА ПРАКТИКЕ (4 страницы пилота, 3 параллельных агента, 5+
пушей подряд без единого конфликта в файлах страниц): каждая перенесённая
страница пилота — это ПОЛНОСТЬЮ ОТДЕЛЬНЫЙ mini-Vite-проект в своей папке
(web-history/, web-milestones/, web-calendar/), с собственными
package.json/vite.config.ts/tsconfig и СОБСТВЕННЫМИ копиями общих кусков
(date.ts, theme.ts, i18n.ts, supabase.ts, AppShell.vue) — код между
страницами НЕ импортируется через общий пакет, а дублируется. Прямое
следствие: миграция любой НОВОЙ страницы (своя папка) НЕ конфликтует ни с
одной другой парой web-*/*-vue уже в работе.

ЕДИНСТВЕННАЯ реальная точка коллизии на практике (столкнулись дважды за
сессию) — SITE_VERSION и CHANGELOG_RU/CHANGELOG_EN в config.js: несколько
агентов вставляют свою запись в самое начало массива и бампают версию
одновременно → merge conflict именно в этих 2 строках + верхней записи
массива. Это НЕ страшно и решается за минуту (см. ниже), но НЕ путать с
конфликтом файлов страницы — сам код страниц не пострадал ни разу.

Как разрешать конфликт SITE_VERSION/CHANGELOG при пуше:
  1. git fetch origin && git log --oneline origin/main -5 — посмотреть, кто
     уже запушил и на какой версии остановился.
  2. Если разошлись — git merge origin/main (не --ff-only, раз есть
     локальные незапушенные правки config.js) или git stash → merge → stash
     pop, если правки нужно сохранить поверх.
  3. В конфликте — ОБЕ записи остаются, порядок по номеру версии (больший
     сверху); SITE_VERSION = наибольший номер + 1 (не наибольший из двух —
     если A взял 0.73 и B тоже метил в 0.73, после мержа правильный итог
     0.74, не "оставить один 0.73").
  4. node --check config.js, потом commit, потом ЕЩЁ РАЗ git fetch перед
     push (за время резолва конфликта кто-то мог успеть запушить снова).
  5. Не переживать из-за "потраченного" номера версии — пропуски в нумерации
     не проблема, страшнее — молча перезаписать чужую запись при выборе "at
     mine" вместо честного мержа обеих.

Деплой не имеет общего wrangler-конфига (автодетект статики в корне) — новую
папку web-<page>/*-vue/ не нужно никуда отдельно прописывать, просто
закоммитить.
