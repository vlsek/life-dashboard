## Честная модель угроз

Почти все данные, из которых складываются баллы, пользователь вводит сам (`daily_values`: политика «for all, user_id = auth.uid()»).
Поэтому «накрутить» себе баллы можно принципиально — и это нельзя закрыть одной миграцией: нужна серверная проверка каждого ввода.
Значит, защита покупок осмысленна там, где (а) страдают ДРУГИЕ люди (права админа, чужие аккаунты, рамки в Сообществе), и
(б) нужна целостность (нельзя получить предмет без списания из-за сбоя, нельзя «вернуть» потраченное, нельзя выдать себе валюту без ограничений).

### №1 — самовыдача прав администратора (КРИТИЧНО, исправлено в 059, нужно применить)

`admin_list_users()` и `admin_delete_user()` (`009`, `011`) — SECURITY DEFINER; единственная проверка — `profiles.is_admin = true`.
Политика `own profile` разрешает владельцу строки менять её целиком, в том числе `is_admin`. Цепочка, воспроизведённая на стенде:
`update profiles set is_admin = true where user_id = <я>` → `admin_list_users()` отдаёт почты всех пользователей →
`admin_delete_user(<чужой id>)` удаляет чужую учётную запись (стенд показал: жертва действительно исчезла из `auth.users`).
Исправление — миграция `059_protect_admin_flag.sql`: триггер запрещает ролям приложения (`authenticated`, `anon`) создавать профиль с
`is_admin = true` и менять флаг. Админа по-прежнему выдают вручную в SQL Editor (он работает не под этими ролями). Клиентский код `is_admin`
не пишет, поэтому ничего не ломается. Стражи: триггер, который ничего не блокирует, — 4 красных; триггер, блокирующий и SQL Editor, — сценарий падает.

**Что сделать владельцу:** (1) применить `059`; (2) проверить, не пользовался ли кто-то дырой до исправления: в SQL Editor выполнить
`select p.user_id, u.email, p.display_name, p.is_admin from profiles p join auth.users u on u.id = p.user_id where p.is_admin;`
— в списке должны быть только вы; незнакомый админ означает, что дырой воспользовались; (3) заодно сверить число пользователей с ожидаемым.
Миграция уже выданные права НЕ отзывает — это делается вручную: `update profiles set is_admin = false where user_id = '…';`.

### №2 — бонусные монеты (051)

Политика разрешает вставку любой строки `(user_id = я, key, coins ≤ 500)`; первичный ключ `(user_id, key)` лишь не даёт выдать один и тот же ключ дважды,
но ключей можно придумать сколько угодно. Решение: серверный каталог наград (`achievement_reward_catalog(key, coins)`) и функция
`grant_achievement_bonus(key)`: сумма берётся из каталога, а не от клиента; прямую вставку клиенту закрыть. Проверка того, что значок
действительно заслужен, упирается в то, что значки сейчас вычисляются на клиенте (`user_achievements` пишет клиент) — серверная сверка условия значка
остаётся отдельной большой задачей (так записано и в 051). Каталог по крайней мере ограничит ущерб известным набором наград.

### №3, №5, №6 — покупка предметов (срез 2)

Модель по образцу огоньков (`057_streak_sparks.sql`: клиент только читает журнал, пишут серверные функции — так сделано правильно):
- таблица цен `customization_catalog(item_key, price, source)` (цены сейчас лежат только в клиентском реестре);
- функция `buy_customization(item_key)` (SECURITY DEFINER): блокирует строку профиля `for update` (две вкладки не купят одновременно), проверяет
  «не куплено», считает баланс на сервере (`calc_user_points` + бонусы − потрачено), в ОДНОЙ транзакции пишет предмет и списание; идемпотентна;
- функция выдачи наград-предметов за достижения; клиенту закрыть `insert/update/delete` в `user_customizations`;
- ограничение на `profiles.customization`: выбрать можно только открытый предмет (триггер); сейчас чужие это уже не увидят (`get_public_frames`, 049, проверяет
  наличие строки), но проверка опирается на строку из №3.

### №4 — журнал потраченного (срез 4) — ИСПРАВЛЕНО в 065 (нужно применить)

Охранный триггер на `shop_items`, как `shop_items_sparks_guard` для огоньков, но для монет: строку покупки Кастомизации нельзя изменить или удалить с клиента.
(Желания Магазина — личные цели пользователя; их цену и пометку «куплено» он задаёт сам, это не защищаемая граница.)

## Режим отладки (47.4) — что учесть, чтобы он не стал новой дырой

- Админ определяется ТОЛЬКО флагом, защищённым 059. Режим отладки — отдельный флаг `profiles.debug_mode`, менять который можно только функцией
  `set_debug_mode(on boolean)`, проверяющей `is_admin` на сервере; расширить триггер из 059 на этот флаг.
- «Примерка» — только на клиенте: предмет показывается, но НЕ пишется ни в `user_customizations`, ни в `profiles.customization`, не списывает монеты и не выдаёт достижений
  (иначе другие увидят платный предмет, а проверка владения в `get_public_frames` и в серверной покупке перестанет быть верной). По выключению режима состояние откатывается.

### №4 — как устроено исправление (миграция 065)

- Строки, созданные серверной покупкой `buy_customization`, помечаются `shop_items.source = 'customization'`. Помеченную строку ролям приложения нельзя ни изменить, ни удалить (ошибка 42501); снять пометку тоже нельзя. Клиентская вставка с `source` пометку теряет (всегда «обычная» строка).
- Желания Магазина (`source IS NULL`) работают как раньше: личные цели, их цену и «куплено» пользователь задаёт сам — это не защищаемая граница. Магазин и так прячет строки Кастомизации из списка (`isCustomizationPurchase`), поэтому кнопок «удалить» у них нет и клиент не меняется.
- Старые покупки (до 065) помечаются по префиксу «Кастомизация:» / «Customization:» — тому же, что использует магазин. Известное ограничение: старая покупка, у которой имя не начиналось с префикса (ручная правка), останется «обычной».
- SQL Editor, функции `SECURITY DEFINER` и каскад при удалении аккаунта работают не под ролями приложения — охрана их не задевает (проверено сценарием: владелец БД удаляет помеченную строку, удаление аккаунта чистит журнал).
- Проверка: `scripts/sql_harness/scenario_065_purchase_journal.sql` (14 проверок) и `scenario_audit_security.sql` (осталась красной только проверка значков — срез 6). Мутации триггера (не охраняет удаление, можно снять пометку, пометка клиента остаётся, покупка не ставит пометку, охрана и для владельца БД) ловятся.
- Применять после 060 (нужна `buy_customization`). Повторный запуск безопасен. Проверка результата: `docs/sql-checks/065_protect_purchase_journal_check.sql`.
