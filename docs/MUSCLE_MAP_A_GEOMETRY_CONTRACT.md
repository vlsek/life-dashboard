# Контракт геометрии A — «Анатомическая студия»

Статус: исследовательский WIP, 2026-11-08. Production не подключён.

## Зачем

Вариант A должен быть **другой геометрией**, а не очередной раскраской текущих FRONT_SHAPES / BACK_SHAPES. Карта остаётся учебной 2D-схемой крупных мышечных групп, не медицинским атласом и не инструментом диагностики.

Рабочая гипотеза: A — основной кандидат для дальнейшей реализации. Это не означает согласие на production-интеграцию: текущий срез ограничен контрактом и изолированным прототипированием.

## Текущая точка отсчёта

- Канонический тип — 12 MuscleId из shared/body-picker/muscles.ts.
- В production «Тренировок» MuscleMap.vue получает bodyGeometry(model); anatomy / atlas / tech меняют в основном стиль, а не геометрию.
- shared/body-picker/bodyModel.ts преобразует существующие пути в женский силуэт через feminizePath. Это общий модуль: его изменение может затронуть и «Дашборд».
- Существующие расчёты нагрузки, выбор мышцы, список упражнений, история и события компонента не относятся к задаче геометрии и должны остаться без изменений.

## Обязательная матрица геометрии

Должны существовать четыре явно различимые проекции, а не один набор путей, который автоматически растягивается:

| Модель | Проекция | Отдельный контур тела | Отдельные мышечные контуры |
|---|---|---|---|
| male | front | да | да |
| male | back | да | да |
| female | front | да | да |
| female | back | да | да |

Общий viewBox и общие правила именования допустимы. Повторное использование отдельных технических утилит для построения зеркальных левой/правой сторон допустимо. Автоматическое преобразование всей мужской геометрии в женскую через единый коэффициент ширины — не считается независимой моделью.

### Покрытие 12 MuscleId

Не каждая группа обязана быть видна с обеих сторон. Отсутствие мышцы на проекции должно быть анатомически объяснимо, а не следствием пропуска данных.

| MuscleId | Front | Back | Примечание |
|---|---:|---:|---|
| chest | ✓ | — | грудные |
| shoulders | ✓ | ✓ | передняя/задняя дельта; единая группа выбора |
| biceps | ✓ | — | передняя поверхность плеча |
| triceps | — | ✓ | задняя поверхность плеча |
| forearms | ✓ | ✓ | отдельные сегменты сгибателей/разгибателей; не одна широкая «варежка» |
| abs | ✓ | — | прямая мышца живота; косые/глубокие структуры — дополнительный слой |
| back | — | ✓ | широчайшие и трапециевидная область в пределах одной группы |
| lower_back | — | ✓ | разгибатели поясницы; визуально отделить от широчайших |
| glutes | — | ✓ | левая/правая ягодичные области |
| quads | ✓ | — | передняя поверхность бедра |
| hamstrings | — | ✓ | задняя поверхность бедра |
| calves | ✓ | ✓ | передняя/задняя проекции голени; задняя икра должна читаться отдельно |

Покрытие проверяется по множеству уникальных MuscleId, а не по количеству SVG-путей: у одной группы может быть несколько самостоятельных брюшек.

## Контракт данных для будущего адаптера

Рекомендуемая форма (названия полей можно уточнить при реализации, смысл сохраняется):

    type MuscleLayer = 'surface' | 'deep'
    type BodyProjection = 'front' | 'back'
    type MuscleRegion = {
      id: MuscleId
      region: string
      side: 'left' | 'right' | 'center' | 'bilateral'
      layer: MuscleLayer
      d: string
      hitD?: string
    }
    type ProjectionGeometry = {
      viewBox: '0 0 100 190'
      outline: string
      regions: MuscleRegion[]
    }
    type ModelGeometry = {
      male: { front: ProjectionGeometry; back: ProjectionGeometry }
      female: { front: ProjectionGeometry; back: ProjectionGeometry }
    }

- id всегда один из 12 канонических MuscleId; новые значения не добавлять.
- region уникален внутри проекции и модели. Примеры: forearm-flexor-left, forearm-extensor-right.
- side нужен для зеркальных областей и будущих подписей; bilateral допустим для одной интерактивной области, объединяющей симметричную пару. Он не создаёт отдельный MuscleId.
- layer задаёт порядок отрисовки: сначала deep, затем surface. Переключатель слоя — отдельная UX-задача, не обязательная часть первого среза.
- hitD не обязан совпадать с видимой анатомической формой. Кликабельная зона должна быть достаточно широкой для телефона и не перекрывать соседнюю группу.
- Для каждого региона SVG должен быть самостоятельным контуром; не использовать CSS-фильтры/обводки как замену анатомическим формам.
- Цвет/прозрачность/выбор/heat вычисляются из существующего состояния компонента и применяются ко всем регионам с одинаковым id.

## Инварианты интеграции

1. Стабильные 12 MuscleId и их локализация остаются единственным источником идентичности мышц.
2. Выбор любого региона выбирает всю группу с тем же id; выбор из списка подсвечивает все её регионы на обеих проекциях.
3. data-muscle, aria-label, aria-pressed, Enter/Space и видимый focus ring остаются на интерактивной зоне.
4. Неиспользуемые регионы другой проекции не должны оставаться в DOM с активной подсветкой.
5. Heat-состояние (recent / volume / covered) применяется одинаково к каждому региону одной группы.
6. Геометрия не содержит бизнес-логики, запросов, localStorage, вычисления статистики или знания о тренировках.
7. Сначала deep, затем surface; интерактивные зоны не должны перехватывать клик по другой группе.
8. Текущие стили anatomy / atlas / tech не объявлять независимыми моделями тела.

## Проверки перед подключением

- [ ] В каждой из четырёх проекций контур тела и мышечные регионы заданы явно.
- [ ] Множество уникальных id каждой проекции точно совпадает с таблицей покрытия выше.
- [ ] Нет неизвестных MuscleId, повторяющихся region и пустых SVG-путей.
- [ ] Для каждой группы проверено, что выбор из списка подсвечивает все её регионы.
- [ ] Проверены независимость мужской и женской формы, отсутствие обрезанных путей и перекрытий hit areas.
- [ ] Мутационные тесты: удалить обязательную группу, подменить MuscleId, убрать hitD у узкой зоны — соответствующие проверки должны упасть.
- [ ] Chromium: 1280, 390 и 360 px; обе темы; клавиатура; отсутствие горизонтальной прокрутки и ошибок консоли.
- [ ] NVDA/VoiceOver и реальное устройство отмечаются отдельно, не выдаются за пройденные проверки.
