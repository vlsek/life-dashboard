# Портфолио + личный дашборд

Структура: публичная визитка (`index.html`) + защищённый логином трекер (`dashboard.html` и остальные).

## Шаг 1 — Supabase проект

Если ещё нет проекта — https://supabase.com → New project. Если уже есть с прошлой версии —
**эта схема несовместима со старой** (был текстовый user_id "просто имя", стал настоящий аккаунт),
проще создать новый проект или почистить старые таблицы перед запуском новой схемы.

## Шаг 2 — таблицы и логика

SQL Editor → New query → вставь всё содержимое `schema.sql` → Run.

Это создаст таблицы **и** триггер: при регистрации нового пользователя ему автоматически
заводятся 6 стандартных метрик (отжимания, вода, учёба, калории, тренировка, мир с близкими) —
чтобы не начинать с пустого дашборда.

## Шаг 3 — настройки авторизации

Authentication → Providers → Email — должен быть включён по умолчанию.

Для быстрого теста (без настройки почтовых писем) можно отключить подтверждение email:
**Authentication → Settings → Email Auth → "Confirm email"** → выключить.
Тогда регистрация сразу пускает в аккаунт без перехода по ссылке из письма.
Если хочешь оставить подтверждение — тоже нормально, просто после регистрации
нужно будет проверить почту.

## Шаг 4 — ключи в config.js

Project Settings → API:
- **Project URL** → `SUPABASE_URL` (без `/rest/v1/` на конце)
- **Publishable key** (он же anon/public) → `SUPABASE_ANON_KEY`

**НЕ используй Secret key** — это ключ полного доступа в обход всех ограничений, ему не место
в коде страницы, которую видит браузер.

Открой `index.html` и `portfolio.css`, замени:
- Заголовок и specialization в hero-блоке
- Ссылки LinkedIn/GitHub/почта
- Блок "Обо мне"

## Шаг 6 — хостинг

Как и раньше — Netlify Drop (перетащи всю папку) или GitHub Pages. **Зарегистрируйся в Netlify
перед заливкой** (займёт 30 секунд) — иначе сайт временно закроют паролем до подтверждения.

## Как пользоваться

1. На визитке — кнопка "Личный дашборд →" ведёт на `login.html`
2. Регистрируешься email + паролем (это твой личный аккаунт, данные видны только тебе — Row Level
   Security на уровне базы, а не просто "разделение по имени", как было раньше)
3. Дашборд → кнопка "⚙️ Настроить метрики" — открывает всплывающее окно, где можно
   добавить/изменить/удалить любую метрику дня: название, иконка, тип (число / да-нет /
   выбор из вариантов), цель и единицы измерения
4. Вода теперь по умолчанию в мл (цель 2500), не в литрах — как просил

## Известные ограничения (сразу говорю честно)

- **Окно добавления метрики одно на все типы** — при выборе "число" появляются лишние поля
  "варианты для выбора" и наоборот, они просто не используются в зависимости от типа. Можно
  причесать (условные поля в модалке), но это отдельная доработка интерфейса — скажи, если
  бросается в глаза, поправлю.
- **Баллы по дням считаются по ТЕКУЩЕМУ набору метрик** — если добавишь/удалишь метрику,
  это не пересчитывает задним числом "сколько могло быть баллов" в старые дни точно
  по тем метрикам, что были актуальны тогда. На практике не критично, просто имей в виду.
- Регистрация открыта всем, кто найдёт ссылку — это ожидаемо для email+пароль системы
  (как у любого сайта), но если хочешь закрыть регистрацию только для себя — можно
  отключить публичный signUp и добавлять пользователей только вручную через Supabase
  Dashboard, скажи, настрою.

## CI/CD — как обновлять сайт, не задевая данные людей

Короткий ответ: **фронтенд (файлы сайта) и данные пользователей полностью разделены** — данные
живут в Supabase, файлы сайта нигде не хранят состояние. Значит обновление файлов сайта
физически не может задеть чужие данные. Единственное, что может задеть данные — это
неаккуратные изменения в базе (SQL), для этого ниже отдельное правило.

### Настройка автодеплоя (вместо ручного перетаскивания в Netlify Drop)

1. Залей этот проект в GitHub (создай репозиторий, `git init` → `git add .` → `git commit`
   → `git push`) — если раньше не работал с git, просто попроси меня, соберу пошагово под
   твою ОС
2. Netlify → **Add new site → Import an existing project** → подключи GitHub-аккаунт → выбери
   репозиторий
3. Build command оставь пустым (сайт статический, собирать нечего), Publish directory — `.`
   (корень репозитория)
4. Deploy

После этого **любой `git push` в основную ветку автоматически обновляет живой сайт** за
секунды — без захода в Netlify руками. Это и есть твой CI/CD.

### Правило для изменений базы данных (SQL)

Раз ты теперь публичный многопользовательский сайт — с этого момента **никаких `DROP TABLE`
на живой базе**. Все дальнейшие изменения схемы — только через новый файл в `migrations/`
по образцу `001_categories_follows_onboarding.sql`: `create table if not exists`,
`alter table ... add column if not exists`, `create or replace function` — то есть только
добавление, никогда не удаление существующих структур с данными. Если что-то сломалось и
реально нужно снести — это отдельное осознанное решение, не часть обычного обновления.

`schema.sql` остаётся как есть — это одноразовый файл первой установки, его саму базу
трогать второй раз не нужно.

### Порядок обновлений на практике

1. Правим код (файлы `.html`/`.js`/`.css`) — деплоится автоматически через git push, не
   трогая базу вообще
2. Если нужна новая колонка/таблица — новый файл в `migrations/NNN_описание.sql`, гоняешь
   его в Supabase SQL Editor один раз
3. Обновляем README/список миграций, чтобы не забыть, что уже накатано

### 🐛 Главный баг — пункты в "Целях на сегодня" и в календаре дублировались/ломались
Реальная причина была в схеме БД, не в JS-коде: колонка `daily_notes.planned_goals` была
объявлена как `text[]` (массив строк), а код с самого начала кладёт туда объекты

впихнуть в текстовый массив. При следующей загрузке код видел строку вместо объекта, не
находил по ней цель ("цель удалена") и заново заворачивал её как новый пункт при
сохранении — отсюда двойное/тройное экранирование. Календарь и дашборд пишут в один и
тот же столбец, поэтому баг был одинаковый в обоих местах.

Миграция 012 меняет тип колонки на `jsonb` (правильный тип для объектов) и **репарирует**
уже накопленные испорченные записи — построчно разворачивает вложенное экранирование и
восстанавливает исходные пункты. После прогона миграции зайди в "Цели на сегодня" и в
календарь и проверь, что всё читаемо; если где-то останется совсем каша — напиши, разберём
точечно.

## Обновление — устранено мигание графиков при автосохранении

### 🏋️ Тип метрики "Подходы" — теперь по-настоящему на графиках и в streak, без потери прогресса
Раньше метрики типа "Подходы" (раскрывающийся список с количеством раз + особенностью на
подход) не попадали ни на графики, ни в серверный расчёт баллов/лидерборда/streak — только

и серверный streak, баланс баллов в Магазине, сравнение по категориям в Сообществе — для

(SQL-функция `metric_numeric_value()`). Старые дни, записанные ДО конвертации метрики
(когда там ещё лежало обычное число, а не массив подходов) — читаются как есть, без миграции
данных; функция сама понимает оба формата.

**Требует `migrations/018_sets_type_sql_support.sql`** — переопределяет 5 SQL-функций:
`calc_user_points`, `calc_user_points_for_date`, `calc_perfect_streak`,
`calc_category_streak`, `get_category_leaderboard`. Это самая рискованная миграция из всех
до сих пор — она не создаёт новых таблиц/колонок, а переопределяет уже работающую логику
подсчёта баллов у всех пользователей. Мы не можем прогнать реальный Postgres в процессе
разработки, чтобы проверить её вживую — пожалуйста, после прогона миграции **проверь баланс
баллов и streak на своём аккаунте**, что цифры не поехали, прежде чем сообщать проекту
знакомым/друзьям, которые тоже пользуются дашбордом.

Заодно форма метрики теперь разблокирует поля "Цель"/"Единица измерения" и для типа
"Подходы" (раньше только для "Числа") — при конвертации существующей метрики цель
сохраняется и продолжает работать (сравнивается с суммой reps).

**Известное ограничение**: если открыть на карточке дня дату ДО конвертации метрики в
"Подходы", список подходов будет выглядеть пустым (там ведь физически лежит старое число,
а не массив) — это только визуально для той карточки, на графиках/streak/баллах эти старые
дни по-прежнему учитываются корректно. Также кнопка "✏️ Изменить значения" под графиком
теперь скрыта для метрик типа "Подходы" — редактирование одним числом там перезаписало бы
весь список подходов за день, это оставили только для карточки дня.
